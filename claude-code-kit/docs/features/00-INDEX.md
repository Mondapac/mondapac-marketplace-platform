# سند جامع قابلیت‌ها (Feature Specification) — پلتفرم Marketplace

**مرجع تحلیل:** مستندات کاربری Bagisto (هستهٔ فروشگاهی: docs.bagisto.com) و مستندات افزونهٔ Multi-Vendor Marketplace (marketplace-docs.bagisto.com)
**دامنهٔ سند:** فقط «چه قابلیتی، با چه قواعدی». معماری و Stack عمداً خارج از این سند است و جداگانه تصمیم‌گیری می‌شود.
**تاریخ تحلیل:** ۲۸ سپتامبر ۲۰۲۶

> این سند رونویسی از مستندات Bagisto نیست؛ قابلیت‌ها و قواعد کسب‌وکار استخراج و به زبان مستقل و قابل‌پیاده‌سازی بازنویسی شده‌اند. فایل ۰۷ شامل بهبودهای پیشنهادی نسبت به Bagisto است؛ قابلیت‌های اختصاصی ما (چارچوب عمومی گواهی در فایل ۰۸، بین‌المللی‌سازی و مدیریت بازار در فایل ۰۹) در Bagisto اصلاً وجود ندارند.

---

## ۱. صداقت دربارهٔ سطح پوشش

همهٔ صفحات یک‌اندازه بررسی نشدند. برای هر بخش سطح پوشش مشخص است:

| سطح | معنا |
|---|---|
| **عمیق** | صفحه به‌طور کامل خوانده و قواعد دقیق استخراج شده است |
| **خلاصه** | فقط از معرفی و فهرست سایت مستندات استنباط شده؛ قبل از پیاده‌سازی باید صفحهٔ مرجع (یا رفتار محصول) بررسی شود |

**پوشش عمیق:** معرفی Marketplace، ثبت‌نام فروشنده، مدیریت فروشنده، Seller Attributes، Account Health، Product Approval، Selling Existing Products، Bulk Upload، تنظیمات Sellers و Products، Commission، Payment/Payout، Mass Payout، Subscription Plans، Order Management، Fulfilment Carriers، RMA (سمت مارکت‌پلیس و هستهٔ فروشگاه)، Communications، Flagging، Shopping Across Sellers، Checkout Deals، صفحهٔ Products، Cart Rules.

**پوشش خلاصه:** Catalog Rules، Product Discounts و Joining Admin Discounts، Campaigns/Email Templates/Events/Newsletter، Taxes، Channels، Locales/Currencies/Exchange Rates، Checkout/Order/Invoice Settings، GDPR، Data Transfer، Themes و Section Types، Reporting (فروش/مشتری/محصول/فروشنده)، Generative AI، Featured Sellers، Landing Page، Seller Shop Page، Ratings، Product Barcode، Product Form Layout، Booking، و افزونه‌های B2B و Multi-Tenant و Mobile App.

## ۲. نقش‌ها (Actors)

|---|---|
| Guest | بازدیدکنندهٔ ناشناس؛ خرید مهمان فقط اگر فعال باشد |

| System | زمان‌بند و کارهای خودکار (انقضا، یادآور، محاسبهٔ سلامت) |

## ۳. فهرست فایل‌ها و پیشوند کد قابلیت

| فایل | محتوا | پیشوندها |
|---|---|---|
| `01-sellers.md` | فروشنده، پنل فروشنده، ویژگی‌های فروشنده، سلامت حساب | SEL, PNL, HLT |
| `02-catalog-inventory.md` | دسته، ویژگی، محصول، Offer، تأیید، Bulk Upload، موجودی | CAT, OFR, INV |
| `03-cart-orders-returns.md` | سبد چندفروشنده، سفارش، ارسال، Carrier، مرجوعی | CRT, ORD, SHP, RET |
| `04-money.md` | کمیسیون، پرداخت به فروشنده، تراکنش، اشتراک | COM, PAY, TRX, SUB |
| `05-marketing-customers-moderation.md` | تخفیف، کوپن، مشتری، نظرات، گزارش تخلف، پیام‌رسانی | MKT, CUS, MOD, MSG |
| `06-storefront-admin-platform.md` | ویترین، ظاهر، تنظیمات، گزارش‌ها، AI، افزونه‌ها | STO, ADM, RPT, AIG, EXT |
| `07-improvements.md` | بهبودهای پیشنهادی نسبت به Bagisto | IMP |
| `08-certifications.md` | چارچوب عمومی گواهینامه و مجوز (حلال، کوشر، وگان و قابل‌گسترش) | CERT |
| `09-internationalization.md` | بین‌المللی‌سازی و مدیریت بازار (چندزبانگی، چندارزی، مالیات/پرداخت/انطباق قانونی به‌ازای Market) | INTL |

هر قابلیت یک **کد یکتا** دارد (مثل `SEL-03`) تا در پرامپت، Issue و تست به آن ارجاع بدهید.

> **به‌روزرسانی ۱:** مفهوم «حلال» که ابتدا به‌صورت اختصاصی (`HAL-*` در فایل ۰۷) طراحی شده بود، به یک **چارچوب عمومی گواهی و مجوز** (`CERT-*` در فایل ۰۸) تعمیم داده شد تا کوشر، وگان و هر مجوز دیگری (مذهبی، سلامتی، سبک زندگی) را هم بدون تغییر کد پوشش دهد.
>
> **به‌روزرسانی ۲:** مفهوم «استرالیا» که ابتدا به‌صورت اختصاصی (`AU-*` در فایل ۰۷) طراحی شده بود، به یک **مفهوم عمومی `Market`** (`INTL-*` در فایل ۰۹) تعمیم داده شد تا نیوزیلند، مالزی، اروپا و آمریکا را هم بدون تغییر کد پوشش دهد — طبق چشم‌انداز گسترش بین‌المللی. جزئیات معماری در `docs/architecture/internationalization-architecture.md` و `docs/architecture/country-branch-launch-playbook.md`.
>
> هر دو تعمیم از یک الگوی مشترک پیروی می‌کنند: هسته فقط مفهوم عمومی (CertificationType، Market) را می‌شناسد، نه نمونهٔ خاص آن.

## ۶. نحوهٔ استفاده در Claude Code

۱. این پوشه را در ریپو کپی کنید: `docs/features/`
۲. به `CLAUDE.md` این خط را اضافه کنید:
```
Feature specs live in docs/features/. Before implementing a feature, read the relevant file and
implement only the requested feature IDs. Each ID has business rules; if code and spec disagree, ask.
```
۳. هر بار فقط یک فایل و چند کد را به Claude بدهید تا context پر نشود. پرامپت نمونه (در Plan mode):
```
docs/features/01-sellers.md را بخوان. فقط SEL-01 تا SEL-06 را پیاده کن.
اول مدل دامنه، state machine وضعیت‌های فروشنده و فهرست تست‌های پذیرش را نشان بده
و منتظر تأیید من باش. هر ابهامی در قواعد را قبل از کد بپرس.
```
۴. برای هر کد قابلیت، «معیار پذیرش» را به تست خودکار تبدیل کنید و بعد پیاده‌سازی را بخواهید.
۵. تصمیم‌های خارج از این سند (Stack، معماری) در `docs/adr/` ثبت شود.

## ۷. اصول تمایز از Bagisto

۱. **پرداخت خودکار و قابل‌ردیابی** به‌جای ثبت دستی پرداخت
۲. **ارسال و هزینهٔ ارسال به‌ازای هر فروشنده** در یک سبد
۳. **اعلان‌های کامل** برای همهٔ رویدادهای عملیاتی (مرجوعی جدید، پیام‌ها)
۴. **مدیریت تخلف با آستانه و اقدام خودکار** به‌جای صرفاً شمارش
۵. **اعتماد گواهی/مجوز به‌عنوان مفهوم اصلی و عمومی دامنه** (گواهی، انقضا، بازبینی — برای حلال، کوشر، وگان و هر مجوز آینده، بدون تغییر کد)
۶. **مطابقت قانونی به‌ازای هر Market** (مالیات، ثبت کسب‌وکار محلی، قانون مصرف‌کننده، حریم خصوصی — استرالیا اولین نمونه، نه یک فرض ساختاری)
