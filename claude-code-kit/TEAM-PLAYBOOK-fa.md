# راهنمای تیم Subagent — MondaPac Marketplace Platform

این فایل توضیح می‌دهد چطور ۱۰ نقش تخصصی که در `agents/` ساختیم را در Claude Code هماهنگ کنید.

---

## ۱. یک واقعیت مهم دربارهٔ Subagent ها (قبل از هر چیز بخوانید)

Subagent های Claude Code «تیمی که هم‌زمان دور یک میز می‌نشینند» نیستند. هر Subagent:
- یک **context جدا و تازه** دارد (چیزی از جلسهٔ اصلی یا از Subagent دیگر به‌خودی‌خود نمی‌بیند)
- توسط **جلسهٔ اصلی** (یا خود Claude به‌صورت خودکار بر اساس `description`) فراخوانی می‌شود
- نتیجه‌اش را برمی‌گرداند و کارش تمام می‌شود؛ حافظه‌ای بین فراخوانی‌ها ندارد (مگر `memory` را در تنظیمات فعال کنید)

**پس نقش شما (یا جلسهٔ اصلی Claude Code) همان «مدیر پروژه/ارکستریتور» است** که تصمیم می‌گیرد کدام نقش الان لازم است، به او چه فایل‌هایی بدهد، و خروجی‌اش را به نقش بعدی پاس بدهد. این سند دقیقاً همین جریان کار را مشخص می‌کند.

---

## ۲. نصب

```bash
cp -r claude-code-kit/agents  <ریشهٔ ریپو>/.claude/agents
cp claude-code-kit/CLAUDE.md  <ریشهٔ ریپو>/CLAUDE.md
```
با اجرای `/agents` در Claude Code می‌توانید فهرست ۱۰ نقش را ببینید و در صورت نیاز ویرایش کنید.

## ۴. جریان کار استاندارد برای یک Story

```
۱. product-owner   → از سند قابلیت، Story + معیار پذیرش می‌سازد
۲. software-architect → (اگر غیرتریویال) مدل دامنه/State Machine/مرز ماژول را طراحی می‌کند
۳الف. product-designer → (اگر UI چندمرحله‌ای/چندنقشی دارد) جریان کاربری را طراحی می‌کند
۳ب. backend-developer  → همزمان یا بلافاصله بعد، برش بک‌اند را می‌سازد
۴. ui-ux-designer  → از جریان تأییدشده، مشخصات بصری می‌سازد
۵. frontend-developer → صفحه را طبق مشخصات و API بک‌اند می‌سازد
۶. qa-engineer     → مستقل تست می‌کند، گزارش باگ یا تأیید می‌دهد
۷. security-tester → فقط برای حوزه‌های حساس (هویت، پرداخت، گواهی، RMA/Refund)
۸. qc-release-manager → دروازهٔ نهایی؛ PASS/FAIL با دلیل مشخص
```

نکته: مراحل ۳ب (بک‌اند) و ۳الف→۴→۵ (طراحی و فرانت) اغلب **موازی** قابل انجام‌اند، مخصوصاً اگر از Git Worktree برای دو جلسهٔ همزمان استفاده کنید.

## ۵. نمونه پرامپت‌ها برای فراخوانی صریح

فراخوانی صریح مطمئن‌تر از تکیه بر تشخیص خودکار Claude است، مخصوصاً اوایل کار با این تیم:

```
از عامل product-owner بخواه CERT-10 تا CERT-17 (فایل ۰۸ سند قابلیت‌ها) را
به چند Story کوچک با معیار پذیرش تبدیل کند و ترتیب پیاده‌سازی را پیشنهاد دهد.
```

```
قبل از پیاده‌سازی، از عامل software-architect بخواه مدل دامنهٔ SellerCertification
و State Machine آن (فایل ۰۸، بخش ۲) را طراحی کند، به‌همراه اینکه قانون CERT-21
دقیقاً در کجای معماری enforce می‌شود.
```

```
از عامل backend-developer بخواه Story اول (ثبت گواهی توسط فروشنده) را با تست
دامنه پیاده کند. بعد از اتمام، از عامل qa-engineer بخواه مستقل تست کند و از
security-tester بخواه چون این قابلیت آپلود مدرک و تأیید را شامل می‌شود، بازبینی کند.
```

```
از عامل qc-release-manager بخواه قبل از بستن فاز ۳ بررسی کند همهٔ کدهای
CERT-01..24 و SEL-20..25 طبق فایل ۰۰-INDEX واقعاً کامل و با شواهد (نه فقط ادعا) انجام شده‌اند.
```

## ۶. قوانین هماهنگی (برای جلسهٔ اصلی/شما به‌عنوان ارکستریتور)

1. **context لازم را همیشه صریح بدهید.** هر Subagent فقط فایل‌هایی را می‌بیند که در پرامپت یا با ابزارهای Read/Grep خودش پیدا کند. اگر software-architect باید نتیجهٔ product-owner را ببیند، مسیر فایل Story را در پرامپت بدهید یا از او بخواهید آن را ذخیره کند.
2. **خروجی هر نقش را ذخیره کنید** (`docs/stories/`, `docs/design/flows/`, `docs/adr/`) تا نقش بعدی بدون حدس زدن آن را بخواند — این‌ها را در پرامپت فراخوانیِ نقش بعدی ارجاع دهید.
3. **security-tester و qa-engineer فقط خواننده‌اند** (Edit/Write ندارند)؛ این عمدی است — استقلال بازبینی را حفظ می‌کند. اگر باگ پیدا شد، آن را به backend-developer/frontend-developer برگردانید، Subagent بازبین خودش رفع نکند.
4. **qc-release-manager آخرین مرحله است، نه اولین خط دفاعی.** اگر مستقیم به merge می‌روید بدون QA/Security، این تیم فایده‌ای ندارد.
5. **برای موارد P0 حساس (هویت، پرداخت، گواهی)، عبور از security-tester اختیاری نیست** — این قانون در خود `security-tester.md` و `cto.md` هم تکرار شده.
6. **وقتی دو نقش تعارض دارند** (مثلاً architect و backend-developer دربارهٔ مرز ماژول اختلاف دارند)، `cto` را فراخوانی کنید تا تصمیم نهایی و مستند (ADR) بدهد.

## ۷. مثال کامل یک چرخه (روی CERT-10..17)

```
شما: از product-owner بخواه CERT-10..17 رو به Story تبدیل کنه.
     [ذخیره در docs/stories/certification-seller.md]

شما: از software-architect بخواه با خواندن همون فایل، مدل SellerCertification
     و State Machinش رو طراحی کنه.
     [ذخیره در docs/design/domain/certification.md]

شما: از backend-developer بخواه طبق اون دو فایل Story اول رو پیاده کنه.

شما: از qa-engineer بخواه مستقل تست کنه.
شما: از security-tester بخواه چون آپلود مدرک و workflow تأیید داره، بازبینی کنه.

شما: از qc-release-manager بخواه با دیدن گزارش QA و Security، PASS/FAIL بده.
```

هر مرحله یک فراخوانی جدا و صریح است — این کندتر از «همه‌چیز را یک‌جا بساز» به نظر می‌رسد، اما دقیقاً همان چیزی است که کیفیت یک تیم واقعی حرفه‌ای را شبیه‌سازی می‌کند: هرکس فقط مسئولیت خودش را می‌بیند و مستقل بازبینی می‌کند.
