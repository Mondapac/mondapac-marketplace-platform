# Physical data model — `platform` schema (Phase 1 baseline)

**Author:** Mojtaba (database-designer) — 2026-10-01
**Status:** Approved by the CTO at the Phase 1 review, 2026-10-01 (ADR-0015). The migration
was generated before that approval; design approval comes first from now on.
**Ground truth:** ADR-0004 (decisions 4, 6, 7), ADR-0003, ADR-0005, ADR-0006, ADR-0009
(pattern V4, decisions 6 and 8); IMP-10, IMP-06, CERT-32, SEL-08, VER-08.
**Prisma model:** `prisma/schema/platform.prisma` (`AuditLog`).

## 1. Baseline scope — verdict

The baseline migration contains exactly one table, `platform.audit_log`. Agreed, because:

- It is the only table whose shape is already fixed by an Accepted ADR (0004 decision 7)
  and that does not depend on any module's domain model.
- It exercises everything the up → down → up pipeline must prove early: schema creation,
  a table, secondary indexes, and hand-written SQL (CHECKs, function, triggers) that the
  generated `down.sql` does not cover by itself.
- Outbox/inbox and `platform.event_delivery` (ADR-0006) stay out: their columns and
  indexes depend on the relay's claim query, retry and dead-letter policy, which do not
  exist yet. Designing them without the query is guessing.

One scope note for the CTO: ADR-0009 decision 8 says Phase 1 ships "the audit hash
chain". This baseline does **not** contain it (see 5 and open question Q1).

## 2. Table `platform.audit_log`

Versioning pattern: V4 append-only history (ADR-0009). Market-scoped.

```
platform.audit_log
  id (PK) ── market_id, tenant_id ── occurred_at
  actor_type, actor_id?, acting_as_id?        (ids only, no FK: identity is another schema)
  action ── target_type, target_id
  before?, after? (jsonb) ── correlation_id
```

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | `uuid` | no | PK. UUIDv7 generated by `platform/audit`. No DB default. |
| `market_id` | `varchar(8)` | no | Market code. See 3.1. |
| `tenant_id` | `text` | no | Seam (ADR-0001). No DB default: the writer supplies it. |
| `occurred_at` | `timestamptz(6)` | no | From the injected Clock (ADR-0005), UTC. |
| `actor_type` | `text` | no | `USER` or `SYSTEM` (CHECK). |
| `actor_id` | `uuid` | yes | Identity user id of the real actor; required iff `USER`. |
| `acting_as_id` | `uuid` | yes | Impersonated user (SEL-08 / IMP-06). |
| `action` | `text` | no | `<module>.<subject>.<verb>`, lowercase, e.g. `certification.seller-certification.approved`. |
| `target_type` | `text` | no | `<module>.<type>`, lowercase. |
| `target_id` | `text` | no | Usually a UUID; text because some targets have natural keys (market code, config key). |
| `before` | `jsonb` | yes | JSON object; null for creations. |
| `after` | `jsonb` | yes | JSON object; null for deletions. |
| `correlation_id` | `text` | no | Same rule as `platform/logging/correlation-id.ts`: `[A-Za-z0-9._-]{8,128}`. |

PII: **none by design.** `actor_id` / `acting_as_id` / `target_id` are opaque identifiers
(pseudonymous, not encrypted). No name, email, IP address, user agent or free-text reason
column exists, deliberately.

## 3. Decisions

### 3.1 `market_id` is NOT NULL
CLAUDE.md and ADR-0003: every request, job and consumed event resolves to exactly one
market, and core code never falls back to a default. The ADR-0009 hash chain is per
market. A nullable `market_id` would need an exception in the Prisma "unscoped query"
guard and a separate chain. If a real stack-level event appears later (Q2), dropping NOT
NULL is a metadata-only change; tightening a nullable column later is not.

### 3.2 Actor before the identity module exists
`actor_type` (`USER` | `SYSTEM`) plus a plain `actor_id uuid`, no FK (ADR-0004 decision 3).
`USER` covers every authenticated principal regardless of role; roles are identity's data
and are not copied here. `SYSTEM` rows (jobs, workers) have no `actor_id`; the component
is identified by `action` and `correlation_id`. Under impersonation the **real** admin is
the actor and the impersonated user goes in `acting_as_id`, so "who really did it" is
never ambiguous.

### 3.3 `before` / `after` and personal data (ADR-0009 decision 6)
The table is immutable, so personal data written here could never be erased: key
destruction (crypto-shredding) only works for encrypted values, and these columns are
plaintext. Therefore the rule "no personal data in audit before/after" applies from the
first row, not "from Phase 2". The database cannot verify this; it is a requirement on
the `platform/audit` writer (Q4): callers pass an explicit allow-list of fields, never a
whole aggregate. The database only checks that each value is a JSON object.

### 3.4 Append-only enforcement: triggers now, privileges later
- Row trigger rejects `UPDATE` and `DELETE`; statement trigger rejects `TRUNCATE`
  (including `TRUNCATE … CASCADE`). Triggers also bind the table owner and superusers,
  which privileges do not — and today the app connects as the owner.
- `REVOKE UPDATE, DELETE, TRUNCATE` is the second layer, added when devops-engineer
  introduces separate migration and application roles (Q3). Not in this migration: there
  is no role to revoke from.
- Limits, stated honestly: an owner can still `DROP TABLE`, `ALTER TABLE … DISABLE
  TRIGGER` or set `session_replication_role = replica`. Detecting that is the job of the
  hash chain (VER-08), not of the trigger.
- Side effect: integration-test cleanup that truncates all tables will fail on this
  table. Tests must use a fresh database/template per run or transaction rollback; do not
  add a bypass to the trigger.

### 3.5 Hash chain is a separate, later table
The sealer (ADR-0009 V4) will write to its own append-only table (working name
`platform.audit_log_seal`: `market_id`, `chain_seq`, `audit_log_id`, `prev_hash`,
`row_hash`, `sealed_at`) in the slice that implements it. Alternative considered: seal
columns on `audit_log` filled by one allowed `UPDATE`. Rejected for the baseline because
it weakens "no UPDATE ever" to "one carefully-permitted UPDATE", doubles the writes per
row (dead tuple per sealed row), and forces hash columns to be designed before the
canonical hashing is specified. Cost of the chosen option: the sealer finds unsealed rows
by anti-join, which needs a bounded scan window; that is designed with the sealer.

### 3.6 Deliberately not included
- `recorded_at` (database clock): `@default(dbgenerated("now()"))` produces permanent
  drift in `prisma migrate diff` (measured), and `@default(now())` is filled by the
  client, not the database. Not worth a trigger until someone needs it.
- `reason`, IP address, user agent: personal or free-text data in an immutable table.
- Status/role copies, FK to any other schema.
- `version` column: rows are never updated.

## 4. Access paths

Volume assumption (MVP, one market, Greater Brisbane): 10²–10³ rows/day, under 1M
rows/year. Measured on PostgreSQL 16 with 300k synthetic rows: about 250 B/row heap and
310 B/row across the three indexes, so roughly 0.6 GB/year at the upper bound.

| Query | Index | Measured (300k rows) |
|---|---|---|
| History of one entity, newest first (CERT-32) | `(market_id, target_type, target_id, occurred_at)` | backward index scan, 19 buffers, 0.07 ms |
| Actions of one actor in a period (IMP-06) | `(market_id, actor_id, occurred_at)` | backward index scan, 55 buffers, 0.46 ms |
| Admin audit list, keyset on `(occurred_at, id)` | `(market_id, occurred_at, id)` | backward index scan, 8 buffers, 0.09 ms |

Not added, on purpose (no concrete query yet; each costs every insert):
- `correlation_id` — debugging lookup; add when an admin/support screen needs it.
- `action` — filter on the admin list; served acceptably by the time index at MVP volume.
- `acting_as_id` — impersonation review goes through the actor index.
- GIN on `before` / `after` — nothing searches inside the JSON.

All indexes lead with `market_id`; every query on this table must carry it.

## 5. Growth, partitioning, retention

- No partitioning in the MVP. Prisma cannot model a partitioned table, and a partition
  key would have to join the primary key. Revisit at about 50M rows or when a retention
  policy requires dropping old data. Path: create a range-partitioned parent on
  `occurred_at`, add a matching unique index to the existing table concurrently, attach
  it as the first partition. No rewrite.
- Retention: keep everything until a Market retention configuration exists (Q5).
  Deleting is impossible by design; retention will be partition detach/drop, run by the
  owner role, and must respect the hash chain (sealed checkpoints).
- Insert-only table: no bloat; autovacuum only needs to freeze and keep the visibility
  map current. Defaults are sufficient.

## 6. Hand-written migration SQL

Prisma generates `CREATE SCHEMA IF NOT EXISTS "platform"`, the table, the PK and the three
indexes. Append the following to the generated `migration.sql`, unchanged.

```sql
-- Hand-written (database-designer): integrity backstops Prisma cannot express.
ALTER TABLE "platform"."audit_log"
  ADD CONSTRAINT "audit_log_market_id_check" CHECK ("market_id" <> ''),
  ADD CONSTRAINT "audit_log_tenant_id_check" CHECK ("tenant_id" <> ''),
  ADD CONSTRAINT "audit_log_actor_type_check" CHECK ("actor_type" IN ('USER', 'SYSTEM')),
  ADD CONSTRAINT "audit_log_actor_check" CHECK (("actor_type" = 'USER') = ("actor_id" IS NOT NULL)),
  ADD CONSTRAINT "audit_log_acting_as_check" CHECK ("acting_as_id" IS NULL OR ("actor_id" IS NOT NULL AND "acting_as_id" <> "actor_id")),
  ADD CONSTRAINT "audit_log_action_check" CHECK ("action" ~ '^[a-z0-9]+([.-][a-z0-9]+)*$' AND char_length("action") <= 128),
  ADD CONSTRAINT "audit_log_target_type_check" CHECK ("target_type" ~ '^[a-z0-9]+([.-][a-z0-9]+)*$' AND char_length("target_type") <= 128),
  ADD CONSTRAINT "audit_log_target_id_check" CHECK (char_length("target_id") BETWEEN 1 AND 128),
  ADD CONSTRAINT "audit_log_before_check" CHECK ("before" IS NULL OR jsonb_typeof("before") = 'object'),
  ADD CONSTRAINT "audit_log_after_check" CHECK ("after" IS NULL OR jsonb_typeof("after") = 'object'),
  ADD CONSTRAINT "audit_log_correlation_id_check" CHECK ("correlation_id" ~ '^[A-Za-z0-9._-]{8,128}$');

-- Hand-written (database-designer): append-only enforcement (ADR-0004 decision 7, ADR-0009 V4).
CREATE FUNCTION "platform"."audit_log_reject_mutation"() RETURNS trigger
  LANGUAGE plpgsql
AS $$
BEGIN
  RAISE EXCEPTION 'platform.audit_log is append-only: % is not allowed', TG_OP
    USING ERRCODE = 'restrict_violation';
END;
$$;

CREATE TRIGGER "audit_log_no_update_delete"
  BEFORE UPDATE OR DELETE ON "platform"."audit_log"
  FOR EACH ROW EXECUTE FUNCTION "platform"."audit_log_reject_mutation"();

CREATE TRIGGER "audit_log_no_truncate"
  BEFORE TRUNCATE ON "platform"."audit_log"
  FOR EACH STATEMENT EXECUTE FUNCTION "platform"."audit_log_reject_mutation"();
```

Complete `down.sql` (`prisma migrate diff` produces only the `DROP TABLE` line):

```sql
DROP TRIGGER "audit_log_no_truncate" ON "platform"."audit_log";
DROP TRIGGER "audit_log_no_update_delete" ON "platform"."audit_log";
DROP TABLE "platform"."audit_log";
DROP FUNCTION "platform"."audit_log_reject_mutation"();
```

Notes:
- `CREATE FUNCTION` is intentionally not `OR REPLACE`, and the down has no `IF EXISTS`:
  if the down forgets an object, the second up in CI fails instead of passing silently.
- The down leaves the empty `platform` schema in place; the up uses `IF NOT EXISTS`.
- SQLSTATE `23001` (`restrict_violation`) lets the application treat a rejected mutation
  as an integrity error.
- Lock impact: none that matters; the table is new and empty.

Verified on PostgreSQL 16 in a scratch database (dropped afterwards): up → down → up
succeeds; each CHECK rejects its bad row; UPDATE, DELETE, TRUNCATE and TRUNCATE CASCADE
are rejected; `prisma migrate diff` from the migrated database to the schema is empty (no
drift from the hand-written objects). Docker Compose runs PostgreSQL 17; nothing here is
version-specific.

## 7. Open questions for the CTO

- **Q1 — Hash chain in Phase 1?** ADR-0009 decision 8 puts the audit hash chain in
  Phase 1; the orchestrator's scope is "table only, no writer". Recommendation: ship the
  table now, and the seal table together with the writer and sealer (canonical row
  encoding and hash need software-architect and security-tester input). Confirm, and
  confirm the separate-seal-table direction (3.5).
- **Q2 — Stack-level audit events.** Are there audited actions with no market (creating a
  Market, Region Stack configuration)? Current design says no (`market_id` NOT NULL).
- **Q3 — Database roles.** When do separate migration/owner and application roles arrive
  (devops-engineer)? The `REVOKE UPDATE, DELETE, TRUNCATE` layer depends on it.
- **Q4 — Writer contract.** `platform/audit` must take allow-listed fields for
  before/after and no personal data from day one (3.3). Needs software-architect to fix
  the port and security-tester to review it, since it sits on the CERT-32 path.
- **Q5 — Retention.** How long must audit rows be kept per Market (AU tax/consumer-law
  records)? Needed before partitioning/retention is designed, not before this migration.
- **Q6 — `actor_type` values.** `USER` / `SYSTEM` only. If API clients or service
  accounts become first-class principals, a new value is a small CHECK migration.

9. `_prisma_migrations` stays outside the `platform` schema.
