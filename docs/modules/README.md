# ماژول‌ها — دروازه‌های آمادگی (ADR-0013)

قبل از طراحی و کدنویسی هر ماژول کلیدی، کلیات و امکانات آن با مالک و نقش‌های مرتبط تیم مرور و تأیید می‌شود. این پوشه برای هر ماژول یک «برگهٔ ماژول» دارد: `docs/modules/<module>/brief.md` (قالب: `_template/brief.md`).

## جریان کار هر ماژول

```
برگهٔ ماژول (PO پیش‌نویس می‌کند)
  → G1 دامنه و امکانات (مالک + PO + CTO [+ product-designer])     ← تأیید مالک در برگه ثبت می‌شود
  → طراحی (معمار، database-designer، طراح UI)
  → G2 طراحی (معمار + CTO + database-designer [+ ui-ux + security-tester])  ← مالک: خلاصه + تصمیم‌های لازم
  → برش‌های کد (backend/frontend) → QA → امنیت (سطح A) → QC
```

- **Definition of Ready:** بدون G1 تأییدشده طراحی شروع نمی‌شود؛ بدون G2 تأییدشده (یا دروازهٔ ترکیبی برای سطح B) هیچ کدی نوشته نمی‌شود.
- **تغییر در حین کدنویسی:** فقط همان تغییر یک مرور کوچک می‌گیرد و در «تاریخچهٔ تغییرات» برگه ثبت می‌شود.
- **شکل مرور با مالک:** خلاصهٔ فارسی، سؤال‌ها یکی‌یکی، و نمودار برای جریان‌های پیچیده.
- **موازی‌سازی:** برگهٔ ماژول بعدی در حین کدنویسی ماژول فعلی آماده می‌شود.
- **تمرکز بر تصمیم:** دروازه‌ها برای گرفتن تصمیم‌اند، نه مستندنویسی کامل؛ تصمیم‌های به‌راحتی برگشت‌پذیر عمداً به بعد موکول می‌شوند.

## سطح‌بندی

| سطح | دروازه‌ها | ماژول‌ها |
|---|---|---|
| **A** | G1 + G2 + بازبینی امنیتی | identity، sellers (مدیریت فروشنده)، certification، catalog (محصول، دسته‌بندی، Offer)، inventory، ordering، payments، commission-payouts، tax |
| **B** | یک دروازهٔ ترکیبی | cart، shipping، notifications، search، content (CMS و بلاگ)، legal، promotions |
| **C** | فقط تأیید PO | reporting و قابلیت‌های P2 به بعد بدون اثر روی پول، اعتماد یا دادهٔ شخصی |

**«مدیریت فروش»** یک ماژول واحد نیست: شامل ordering (سفارش)، commission-payouts (کمیسیون و تسویه)، promotions (تخفیف و کوپن) و reporting (گزارش فروش) است و هرکدام با سطح خودش از دروازه عبور می‌کند.

فاز ۱ (اسکلت فنی) فقط به تأیید CTO نیاز دارد.
