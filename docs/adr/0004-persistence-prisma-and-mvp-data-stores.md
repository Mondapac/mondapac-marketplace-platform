# ADR-0004: Persistence — Prisma ORM and MVP Data Stores

**Status:** Accepted — 2026-09-30 (ORM choice made by the owner)
**Supersedes for the MVP:** data-store choices in `docs/spec/technical-spec.md` §1.6–1.7
and §2 (MongoDB for Catalog/Reviews/Notifications, Elasticsearch, Event Store for Order).
Those remain the long-term target, not the day-one stack.

## Context
The modular monolith (ADR-0001..0003) needs one persistence approach that keeps each
module's data private, supports `market_id`/`tenant_id` on every market-scoped table,
stores money as integers and instants as UTC (ADR-0005), and stays simple for a small
team. The spec lists four stores (PostgreSQL, MongoDB, Elasticsearch, Event Store) that
would each need operating in every Region Stack (ADR-0003).

## Decision
1. **Stores for the MVP: PostgreSQL + Redis + S3-compatible object storage (MinIO locally).**
   *(Amended by ADR-0016: MinIO's community images were withdrawn; the local stand-in is
   chosen with the first slice that stores files.)*
   *(Amended by ADR-0018: sessions live in PostgreSQL; there is no token deny-list.)*
   - PostgreSQL: all transactional data. Flexible attributes (AttributeSchema, SEL-20,
     CERT-01) use `jsonb` validated by the owning module. Search starts with PostgreSQL
     full-text search; Elasticsearch is reconsidered by a new ADR in P1 (Search).
   - Redis: sessions/token deny-list, rate limiting, cache. Never the source of truth
     for anything that must survive a restart — carts live in PostgreSQL (`cart` schema,
     market-scoped), with Redis only as a cache in front of them.
   - Object storage: certificate documents (CERT-10), product images; one bucket set per
     Region Stack (ADR-0003).
   - Order history: an append-only status-history table plus domain events (ADR-0006),
     not Event Sourcing. Revisit only with a concrete need.
2. **ORM: Prisma (current major, v7).** Multi-file schema: `prisma/schema/<module>.prisma`,
   one file per module. Each module owns one PostgreSQL schema via Prisma `multiSchema`
   (generally available since 6.13), e.g. `catalog.*`, `ordering.*`.
3. **Boundaries in the persistence layer.**
   - No Prisma `@relation` across module schemas; cross-module references are plain ID
     columns. A CI check fails any relation that crosses schemas.
   - A Prisma client extension rejects any query on a market-scoped model without
     `market_id` in its `where` — this is how "unscoped queries fail" (ADR-0003) is enforced.
   - The Prisma client is imported only from `modules/<m>/infrastructure/` and
     `platform/persistence/` (UnitOfWork, outbox relay). A custom lint
     rule (model→module map generated from the schema files) fails any access to another
     module's models.
   - Prisma models never leave infrastructure: repositories map them to domain objects.
4. **Column conventions.** IDs are UUIDv7 generated by the domain (`@db.Uuid`); instants
   are `@db.Timestamptz` in UTC; money is `BigInt` minor units + `char(3)` currency
   (ADR-0007); every market-scoped table has `market_id` (market code, `varchar(8)`, no FK
   across schemas) and `tenant_id` (`text`, seeded `'mondapac'`), and its indexes lead with
   `market_id`.
5. **Transactions.** A use case runs in one Prisma interactive transaction exposed through
   a `UnitOfWork` bound via AsyncLocalStorage (works for HTTP requests, jobs and event
   handlers alike); the outbox row (ADR-0006) is written in the same transaction. Facade
   calls to another module never join the caller's transaction.
6. **Reversible migrations.** Prisma Migrate generates the up migration; every migration
   folder also holds a `down.sql`, generated with `prisma migrate diff --script` and then
   reviewed. CI applies up → down → up on a fresh database, so the Definition of Done
   ("migrations reversible") is enforced, not assumed.
7. **Audit log.** An append-only `platform.audit_log` table (actor, action, target, market,
   before/after, correlation id), written through `platform/audit` in the same transaction
   as the audited change — required by CERT-32 and SEL-08 (IMP-10). It is platform
   infrastructure like the outbox, not a business module, so this is not a cross-module
   transaction.

## Consequences
- One database per Region Stack with one schema per module keeps operations simple and
  maps 1:1 to "database per service" if a module is extracted later.
- Prisma generates one client for all models; module privacy relies on the lint rule and
  review, not the type system. Accepted trade-off versus one client per module (separate
  migration histories against one database, more tooling friction).
- Down migrations cost extra effort per slice.
- Flexible catalog data in `jsonb` covers the MVP; heavy faceted search is a P1 decision.

## Alternatives considered
- TypeORM: decorator entities pull persistence into the domain model; slower upstream
  maintenance.
- MikroORM: best Unit-of-Work/DDD fit, smaller community; outside the CLAUDE.md defaults.
- Drizzle/Kysely: SQL-first and light, but weaker migration workflow for this team.
- Keep MongoDB/Elasticsearch/Event Store from day one: rejected — four stores to run in
  every Region Stack before the first sale.
